# Z-Cloud AI v1.5.0 — 刷入失败的根因已找到并修掉

## 一句话

之前所有「AccessDenied / InvalidParameter」都不是权限问题，是**载荷长度从一开始就错了**：
机身要 **614 字节**，我们一直发 **84 字节**。槽位编号也偏了 2 位。

---

## 根因（从你发的那份日志里逐字节挖出来的）

你 12:38:38 那次会话的日志里，`0x90CC` 读 C-1 时返回了 **`DATA-IN len=614`**，
而我们的代码当时还在按 84 字节校验，于是把 614 当成了「读回异常」。

我把那两条 614 字节原始数据从日志里导出来逐字节分析，格式是这样的：

| 偏移 | 长度 | 内容 |
|---|---|---|
| `+0x000` | 2 | `02 00` 格式标识 |
| `+0x002` | 20 | ASCII 名称（你的 `Fuji Provia` / `Fuji Astia`） |
| `+0x019` | 1 | `0x08` = 控制点数据字节数 |
| `+0x02C` | 1 | 族标记（Provia=`0x05` / Astia=`0x06`） |
| `+0x02F` | 8 | 4 组 (x, y) 控制点 |
| `+0x066` | **512** | **256 × u16 大端 LUT，值域 0..32767（15 位）** |

`0x66 + 512 = 0x266 = 614`，正好到底，一个多余字节都没有。

**这意味着**：我们发 84 字节，机身按 614 校验长度，长度对不上就直接拒 —— 跟权限、跟前置动作、
跟参数形态全都无关。之前 100 种组合全失败，就是因为 100 种组合的载荷都是错的长度。

## 第二个根因：槽位号偏了 2

你日志里 `0x90CF` 能力查询的输出写得很清楚：

```
0x00C9 → 支持      0x00D0 → 支持
0x00CA → 支持      0x00D1 → 支持
0x00CB → 支持      0x00D2 → InvalidParameter
0x00CC → 支持      0x00D3 → InvalidParameter
0x00CD → 支持      小结：支持 9 项
0x00CE → 支持
0x00CF → 支持
```

**有效区间是 `0x00C9` – `0x00D1`，正好 9 项。** 我们一直用 `0x00CB` – `0x00D3`，整体偏 2：
C-1 实际指到了机身的 C-3，C-8/C-9 指到了根本不存在的 0xD2/0xD3（固定回 0x201D）。
你自己的三个富士配方落在 `0xC9/0xCA/0xCB`，正是机身 C-1/C-2/C-3。

---

## 这一版改了什么

1. **新增 `PcPayload614`**：614 字节格式的解析与构建。读名称、读 256 项 LUT、读 4 组控制点；
   写的时候只覆盖「名称 / 控制点 / LUT」三块，其余 590 字节原样保留（机身对头部有校验）。
2. **槽位改为 `0x00C9`–`0x00D1`**，`isCustomSlot` / `customSlotIndex` / `customSlotFromIndex` 全部同步。
3. **读写链路全线改 614**：`getPicCtrlData` / `setPicCtrlData` / 探测矩阵 / 无损回写 / 批量刷入 /
   `refreshSlots` 的尺寸判断。
4. **曲线没改就不碰 LUT**：机身存 15 位，我们内部 8 位，来回换算会掉精度。
   只改名称的场景，现在保证原记录逐字节不变。
5. **旧 `.NCP` 文件仍能导入**：84 字节旧结构会先解析出来再升级成 614 写入。

## 测试步骤

1. 拔掉电脑数据线，只接 Z30（**同一个 USB-C 口不可能既做 adb 又做 OTG 主机**）。
2. 相机「设定」→「USB」→ 选 **MTP**，不要选「相机控制」。
3. 打开 App → 调试台 → 连接。应当显示 `VID 0x04B0 PID 0x0452`，会话建立。
4. 看「机身 C-1 ~ C-9 槽位实况」：
   - 现在应该能读出 **C-1 = Fuji Provia**、**C-2 = Fuji Astia**、**C-3 = 你第三个配方**
     （之前读不出来的原因是槽位号偏 2）。
   - C-4~C-9 显示「空槽位」是正常的（那 6 个槽确实没存东西）。
5. 到「AI 调色」页，选目标槽位，点刷入。写入后会自动读回校验名称。
6. 成功的话相机拨到对应 C 槽位就能看到效果了。

## 如果这次还是失败

在调试台点「分享日志」，把 `ptp-YYYYMMDD.log` 发我。这次日志里我需要看两行：

- `写入准备 — slot=C-x(0x00Cx) payload=614B`
- 紧随其后的 `CMD 0x90CD params=[...]` → `RESP 0x....`

如果 `payload` 已经是 614B 还被拒，那就是固件对 `0x90CD` 还要求别的条件
（比如必须先「注册/命名」一次，或者必须结束取景）。到时候我按那两行继续挖。

## 已知仍不确定的点

- 614 字节头部的 `0x023 0x01` / `0x024 "I0"` / `0x02A 0x01` / `0x02B 0x0F` 这几字节含义未知，
  现在是从你机身原记录原样继承的（不猜、不改）。
- 写新槽位（没有任何模板可继承）时用的是内置兜底模板，头部按 Provia 的结构复制。
  如果固件对空槽位写入要求别的头部，这一步会失败——失败时日志会显示，再对症处理。
